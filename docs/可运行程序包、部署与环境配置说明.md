# GutCare 可运行程序包、部署与环境配置说明

> 对应竞赛材料第 4 项：可运行程序包、部署文档、环境配置说明。
> 版本：1.0；日期：2026-10-23。
> 本文描述当前仓库可复现的本地测试／演示环境，不构成生产环境部署或医疗服务上线说明。

## 1. 交付内容与运行边界

| 交付内容 | 仓库位置 | 用途 | 运行边界 |
| --- | --- | --- | --- |
| Android 原生客户端源码 | `android/` | 患者端登录、记录、档案、报告候选确认、分析与建议展示 | 唯一客户端开发与验收环境为 Android Studio；旧 `app/` 仅为只读归档 |
| Android 调试 APK | `android/app/build/outputs/apk/debug/app-debug.apk`（由构建生成，不纳入版本库） | 本地模拟器安装与演示 | 仅调试签名；不用于生产分发 |
| 业务后端 | `backend/` | FastAPI 模块化单体、迁移、后台任务与接口契约 | 仅通过业务 API 服务于客户端；客户端不直连数据库、对象存储或智能体 |
| 智能体服务 | `agent/` | 受冻结任务快照约束的候选提取与分析编排 | 默认 mock；live 模式需本地显式配置并仅用于经授权的演示验证 |
| 本地演示编排 | `compose.phone-demo.yaml`、`scripts/phone-demo-*.ps1` | 启动 PostgreSQL、Redis、MinIO、ClamAV、Mailpit、API 和可选智能体 | 项目隔离的测试／演示环境，不能直接视为生产拓扑 |
| 迁移与运行说明 | `docs/部署运维手册.md`、本文 | 运维边界、迁移、健康检查与本地启动说明 | 生产变更仍须遵循部署运维手册中的审批、备份与恢复要求 |

### 1.1 竞赛可运行程序包

竞赛交付 ZIP 位于 `.demo-output/competition-package-20261023-final/GutCare-Competition-20261023.zip`，旁边有 `.zip.sha256` 归档哈希文件，并保留可直接检查的解压树。该 ZIP 本身就是竞赛材料第 4 项的直接提交文件；ZIP 内包含根目录 `README.md`、本文（`docs/可运行程序包、部署与环境配置说明.md`）和 `SHA256SUMS.txt`。清单列出除校验文件自身外每个包内文件的 SHA-256。包包含本地 phone-demo Compose 所需的业务后端、Agent 源码、迁移、契约、MinIO 初始化源码、一键启动/停止/校验脚本、原生 Android Studio 工程、Debug APK、相关部署/演示说明，以及 `demo-materials/competition-demo/` 中已声明从零合成的虚构素材。包不含用户本机 `phone-demo.env`、Agent 私有配置、`.downloads/`、`.runtime/`、缓存、构建中间文件、真实数据或旧 `app/` 归档。

Android APK 使用构建输出目录中已有的 `app-debug.apk`。本地排障记录确认上一轮曾以调试 APK 成功覆盖安装到模拟器；该文件时间晚于当前 Android 主源码文件的最新修改时间。此次重新构建因隔离环境拒绝 Gradle Wrapper 下载（无法连接 `services.gradle.org` 获取 Gradle 9.4.1）而失败。APK 元数据为 applicationId `com.gutcare.app`、debug 变体、版本 `0.1.0`；本轮未重新构建或安装，也未取得该 APK 对应源码输入的可复现证明。评审方可在 Android Studio 从包内源码重新构建与运行。排障证据见 `docs/Android构建与模拟器更新排障记录-20261023.md`。

竞赛包使用独立 Compose 项目 `gutcare-competition-demo`，其命名卷与仓库开发项目 `gutcare-phone-demo` 分开。首次运行时，在解压后的包根目录依次执行：

```powershell
.\Verify-GutCarePackage.ps1
.\Start-GutCareDemo.ps1
```

首次启动会生成仅存放于本机的 `phone-demo.env`，并按需拉取镜像、构建服务及准备固定版本 MinIO 运行时。验收预期为 Compose 启动 22/22；API、Agent 和 dispatchers 健康；一次性 `minio-init` 正常退出；`GET /health/live` 返回 HTTP 200 和 `{"status":"alive"}`；Agent 模式为 `mock`。2026-10-23 已获得上述本机运行证据。启动失败时，启动器会显示竞赛项目最近 80 行 API 日志，并遮盖配置中的密码、Token、密钥和 pepper；不会自动清理容器或数据。

维护者快速复验路径（只适用于已完成首次启动、镜像和本地环境均已准备好的包目录）：

```powershell
docker compose --profile agent -f .\compose.phone-demo.yaml --env-file .\phone-demo.env -p gutcare-competition-demo up -d --no-build --pull never --wait
Invoke-RestMethod http://127.0.0.1:8000/health/live | ConvertTo-Json -Compress
docker compose --profile agent -f .\compose.phone-demo.yaml --env-file .\phone-demo.env -p gutcare-competition-demo exec -T agent python -c "from gutcare_agents.config import load_settings; print(load_settings().mode)"
```

预期分别为服务健康、`{"status":"alive"}` 和 `mock`。该路径不构建或拉取镜像；缺少本地镜像时会直接失败，应改用首次启动步骤。停止时运行 `Stop-GutCareDemo.ps1`；它只停止竞赛项目容器并保留数据库、邮件和上传对象卷，之后可沿用本机配置重新启动。启动后可按包根 `README.md` 在 Android Studio 打开 `android/`。Agent 来源快照未携带 LICENSE；此包仅供竞赛评审，不构成开源许可、赛方再发布或商业分发授权。

## 2. 前置环境

### 2.1 运行本地演示环境

- Windows 10/11；
- Docker Desktop，启用 Docker Compose v2；
- 足够的磁盘空间以保存容器镜像和本地卷；
- 允许 Docker 拉取首次需要的基础镜像和系统包。网络受限时可先使用已缓存镜像，但不得以未知来源镜像替换受控镜像。

### 2.2 构建与运行 Android 客户端

- Android Studio；
- JDK 17（项目 Java 编译目标为 17）；
- Android SDK Platform 36、Build Tools 36；
- 可运行 Android 虚拟设备；本项目本次演示使用 `GutCare_API_37`。模拟器访问宿主 API 使用 `10.0.2.2`，不是 `localhost`。

常规构建应通过 Android Studio 完成。命令行校验脚本会使用临时 ASCII 路径，以规避部分 Windows 工具对非 ASCII 工作路径的兼容性问题，详见 `android/README.md`。

## 3. 本地配置原则

1. 先复制或由脚本生成本地配置，再填写本机值；不提交 `phone-demo.env`、`.env.agent.local` 或任何带密钥的文件。
2. 默认智能体模式是 `mock`，不需要第三方模型密钥，也不会主动向外部模型发出请求。
3. 需要验证 live 模式时，仅在 `.env.agent.local` 或当前受控进程环境中设置模型端点、模型名和访问密钥；启动脚本只验证“是否存在”，不得打印值。
4. 本地演示同意书、示例邮箱和演示数据均为测试用途，禁止输入真实患者资料、真实医疗报告或生产账号。
5. 数据库结构只能通过 Alembic 迁移变更；不使用 ORM 自动修改 schema。

## 4. 启动步骤

在仓库根目录执行：

```powershell
.\scripts\phone-demo-up.ps1
```

该脚本会创建项目隔离的本地演示配置，并启动 API 及其依赖服务。启动完成后可检查：

```powershell
Invoke-WebRequest http://127.0.0.1:8000/health/live
```

预期为成功响应。Mailpit 仅用于本地捕获演示邮件，访问地址由启动输出给出；它不是外发邮件能力。

如需启动包含智能体 worker 的演示配置：

```powershell
.\scripts\phone-demo-agent-up.ps1
```

不额外配置时，该命令应显示请求模式为 `mock`。若因演示验证需要 live 模式，应先按[phone-demo Agent 说明](phone-demo-agent-f08.md)完成本机私有配置，再运行同一脚本；任何密钥均不应出现在终端截图、文档或版本库中。

## 5. Android 构建、安装与验收

1. 在 Android Studio 中打开仓库的 `android/` 目录并等待 Gradle 同步完成。
2. 选择目标虚拟设备，点击 Run；调试客户端默认连接本机 `10.0.2.2:8000` 对应的业务 API。
3. 需要生成调试 APK 时，执行 Android Studio 的 Build APK 操作，或在 `android/` 目录运行：

   ```powershell
   .\gradlew.bat :app:assembleDebug
   ```

4. 生成物位于 `android/app/build/outputs/apk/debug/app-debug.apk`。调试包只能安装到使用同一调试签名的既有应用上；若签名不同，覆盖安装会失败。
5. 安装后必须冷启动应用并验证目标页面。对涉及认证、记录、报告解析或分析的变更，还应按相应 Fxx 文档执行最小接口和 UI 验证。

如果在受限构建环境遇到缓存访问或覆盖安装签名问题，参考[Android 构建与模拟器更新排障记录](Android构建与模拟器更新排障记录-20261023.md)。该记录中的恢复措施不替代完整构建门禁。

## 6. 健康检查、日志与故障定位

| 目标 | 检查方式 | 预期 |
| --- | --- | --- |
| API 存活 | `GET /health/live` | HTTP 成功响应 |
| Compose 服务 | `docker compose -f .\compose.phone-demo.yaml --env-file .\phone-demo.env -p gutcare-competition-demo ps` | API 与依赖服务处于健康/运行状态；一次性初始化容器退出属于预期 |
| API 日志 | `docker compose -f .\compose.phone-demo.yaml --env-file .\phone-demo.env -p gutcare-competition-demo logs --tail=200 api` | 可见结构化请求与错误事件；不得将报告正文或密钥复制到问题单 |
| 智能体 worker | 同一命令将末尾服务名替换为 `agent`、`medical-parse-dispatcher`、`analysis-dispatcher` 或 `record-image-dispatcher` | 任务状态应推进；若停止，优先按 request id 关联 API 与 worker 日志 |

排查时应先确认任务状态与回调结果，再查看模型调用或文件提取环节。不能仅因前端持续显示“处理中”就重建全部容器；这会掩盖任务状态机或回调契约问题。

## 7. 停止、重启与数据清理

普通停止：

```powershell
.\scripts\phone-demo-down.ps1
```

重启服务通常只需再次运行启动脚本。只有明确要删除**该项目的本地演示数据**时，才使用带 `-PurgeData` 的清理操作；这会删除本地数据库与对象存储中的演示内容，不能用于保留历史任务的排障。

## 8. 生产部署差异与交付前门禁

当前 Compose 配置是本地演示拓扑，生产环境至少还需要：受控镜像仓库与签名、独立密钥管理、TLS 与反向代理、数据库备份恢复演练、监控告警、审计留存、容量评估、漏洞修复流程以及真机验收证据。

在满足以下条件前，不得将本地环境用于真实医疗数据处理：

- 已落实数据处理与第三方 AI 授权、撤回和审计流程；
- 已完成生产模型供应商、区域、保留策略与合同审查；
- 已完成完整构建、格式/类型/单元/集成/契约/权限隔离/迁移检查；
- 已完成 Android Studio 模拟器验收和发布前真机证据；
- 已完成备份恢复演练与上线审批。
