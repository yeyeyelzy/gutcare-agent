# ADR-0010：F06 用药计划、日程与打卡

- 状态：已采纳
- 日期：2026-10-15
- 范围：业务后端 F06；不改变智能体边界

## 背景

现有 F06 仅定义了用药计划与打卡的基础语义，尚未冻结来源、重复日程、时区/DST、删除与并发行为。实现前需要明确这些边界，避免把未回应误记为未服用或重写历史。

## 决策

1. `confirmation_status`（`pending/confirmed/needs_review`）独立于 `plan_status`（`active/ended/discontinued`）。只有已确认计划可激活；pending 是持久化未回应状态，绝不等同 `not_taken`。
2. 来源限 `manual` 或同患者 `medical_document`。医疗文档引用使用不含内容/定位/医院信息的稳定墓碑引用（患者、类型、原文档 UUID、可空 live UUID、删除时间）；F02 删除事务先墓碑再删文档/文件，计划仅暴露 `source_deleted`，不因来源删除而级联。
3. 重复日程使用后端解析的受限 RFC 5545 子集：`DAILY`、`WEEKLY`、`INTERVAL`、周规则 `BYDAY`、`COUNT` 和 `UNTIL`，校验非法组合与边界。时区必须为服务端识别的 IANA 名称。
4. DST 不存在的本地时间顺延到该日期首个有效时刻；重复本地时间取第一次。变更时区/日程只重新计算未来 `pending` 实例；已响应记录不改写。
5. 实例物化器为可恢复的独立 CLI，使用事务级 PostgreSQL advisory lock 与唯一约束幂等并发生成有限滚动窗口；锁随事务结束释放，无 lease。通知负载不得包含药品名称、剂量或医嘱内容。
6. 写请求严格 DTO、患者只从认证上下文解析；`Idempotency-Key` 同患者、同摘要重放原响应，摘要不同返回 `409 IDEMPOTENCY_CONFLICT`。隐私删除优先于快照原样重放：医疗文档软删/物理删除与来源墓碑同事务将全部关联 plan-create 响应快照中的 `source_document_id` 置空并将 `source_deleted` 置真；之后同键重放返回该脱敏等价快照，不含正文或定位。可编辑资源携带版本并使用乐观锁。错误按 RFC 9457；其他患者资源统一 404；敏感字段不得写日志。
7. 数据库通过患者复合外键、CHECK、唯一约束、RLS + FORCE RLS 隔离。`gutcare_app` 只得业务所需权限，`gutcare_worker` 仅执行物化所需读取/写入权限，不授予表所有权或绕过 RLS。
8. 不提供药物相互作用分析、剂量推断、处方修改或漏服加倍建议。

## 后果

新增用药计划、日程、打卡及幂等账本迁移和 API 契约。调度时间由日程定义与 IANA 时区计算；数据库保存 UTC `scheduled_for`，并保留本地日期/时刻以支持唯一物化和 DST 审计。测试覆盖 RFC 边界、双状态、历史不变、跨患者隔离、并发幂等、日志脱敏及 PostgreSQL 18 RLS。

## 测试编号修正

现有 F01 已占用 T49–T51。F06 用例从首个未占用编号 T52 开始，不复用或覆盖既有 F01 追踪。

## 独立验收修订

激活计划不能直接进入 `needs_review`；review 返回 RFC 9457 409，需先结束/停用，且不自动更改打卡事实。幂等账本持久化首次状态码及响应快照，后续资源变化不影响重放。F06 追踪只使用 T52–T59。

0010 是含来源墓碑后的 forward-only 数据迁移。墓碑首次产生时，同事务写入仅含固定键与时间戳的全局迁移 marker（不含患者或业务数据）；升级发现既有墓碑时也初始化 marker。downgrade 首个数据库操作只读取该 marker，有值立即拒绝，不能先改 RLS 或执行其他 DDL；marker 用于确保非 BYPASSRLS 迁移角色仍能全局判断且不暴露患者数据。生产应用回滚不得回退 schema，必须部署已通过 0010 schema smoke 的兼容应用制品；发布前做加密业务库备份与对象存储版本/快照，并在隔离库完成恢复校验。
