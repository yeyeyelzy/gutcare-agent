# Android 构建与模拟器更新排障记录

> 日期：2026-10-23
> 适用范围：GutCare 本地演示环境的 Android 原生客户端。本文记录一次本机构建、签名与模拟器覆盖安装的排障过程，不替代正式发布流程。

## 1. 事件概述

完成 Android 前端页面调整后，应用未在已有模拟器中更新。排查过程中先后遇到 Gradle 依赖访问受限、Java 编译阶段无法读取缓存转换产物，以及覆盖安装时签名不一致等问题。问题均发生在本地受限执行环境或既有模拟器安装状态中，不是业务接口、数据库迁移或 Android 源码功能逻辑导致。

本次最终完成了以下闭环：

- 使用本机已有的 Gradle 与依赖缓存生成调试 APK；
- 使用模拟器已安装应用所对应的调试签名完成覆盖安装；
- 核验 APK 签名、设备安装结果与应用进程启动状态；
- 重启应用，保留原有本地登录状态与演示数据；
- 清理为本次排障临时复制的签名材料，不将任何密钥、密码或证书指纹写入仓库。

## 2. 现象、原因与处理

| 现象 | 已确认原因 | 本次处理 | 后续原则 |
| --- | --- | --- | --- |
| Gradle 首次执行试图下载组件，网络请求失败或超时 | 受限运行环境使用了空的临时 Gradle 用户目录，无法复用本机缓存；部分网络出口不可用 | 复用本机已有 Gradle 9.4.1 与依赖缓存，在项目内建立临时构建缓存 | 日常构建优先使用 Android Studio；首次构建前确认网络、代理与 Gradle 缓存可用 |
| Java 编译读取 AndroidX 转换缓存时出现 `AccessDeniedException` | 受限会话对转换后 JAR 的文件访问限制，不是 Kotlin/Java 源码编译错误 | 先核验 Kotlin 编译结果和仅由 Gradle 生成的 `BuildConfig` 产物，再在受限会话中跳过该单一重复任务生成调试包 | 该做法仅适用于本次受限环境；正式验收、CI 与发布必须执行完整 Android Studio/Gradle 构建 |
| 调试 APK 无法覆盖安装，提示签名不兼容 | 本次生成 APK 的调试签名与模拟器中原应用的既有调试签名不同 | 使用应用既有调试签名重新签名 APK，并校验签名一致后覆盖安装 | 不得以卸载应用替代排障，因为会清除本地演示状态；只有获得明确同意且无需保留数据时才可卸载 |
| 已安装但界面未刷新 | 旧进程或旧 Activity 仍在前台 | 覆盖安装后停止并重新启动应用进程 | 每次覆盖安装后均执行一次冷启动，并检查版本安装时间和目标页面 |

## 3. 核验结果

本次以最小、可重复的方式完成核验：

1. 调试 APK 已成功生成；
2. APK 使用既有调试签名重新签名，签名校验通过；
3. 安装工具返回已向一个模拟器设备安装成功；
4. 设备包管理器显示该应用的更新时间已变化；
5. 强制停止并重新启动 `com.gutcare.app` 后，设备返回有效进程号；
6. 未执行演示数据清理，原登录状态与本地演示数据仍保留。

这证明本次前端变更已经进入该模拟器的已安装应用。它不等同于生产发布签名、真机验收或完整 CI 门禁通过。

## 4. 可复用的处置顺序

1. 优先在 Android Studio 打开 `android/` 并运行应用；项目的正式 Android 验收入口仍为 Android Studio。
2. 若构建失败，先区分依赖下载/网络问题、缓存文件访问问题和源代码编译错误，避免将宿主环境错误误判为功能回归。
3. 若 APK 已构建但无法覆盖安装，比较“已安装应用”和“待安装 APK”的签名来源；只有签名所有者可进行重新签名。
4. 覆盖安装完成后，停止并重新启动应用，再观察目标页面；不要仅依赖安装成功提示。
5. 若必须清理应用或模拟器数据，应先明确该操作会删除的范围并征得同意。

## 5. 边界与后续发布要求

- 本记录中的构建缓存复用和单任务规避，是受限会话下的恢复措施，不能写入常规构建脚本或作为发布流程。
- 正式交付必须使用完整构建，执行格式、类型、单元、集成、契约与 Android Studio 模拟器验收；真机证据仍是发布前门禁。
- 正式发布必须使用受控的发布签名、版本号、变更记录和可追溯构建产物；不得复用个人调试签名作为发布签名。
- 与本次演示环境的服务启动、环境变量和健康检查有关的说明，见[可运行程序包、部署与环境配置说明](可运行程序包、部署与环境配置说明.md)。
