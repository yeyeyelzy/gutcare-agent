# GutCare Agent 测试方案

> 版本：V1.0 · 2026-10-14

## 1. 测试层级

| 层级 | 范围 | 发布要求 |
|---|---|---|
| 静态检查 | Ruff/mypy、ESLint/Prettier/vue-tsc、YAML/OpenAPI lint | 0 error |
| 单元测试 | 领域状态机、权限策略、规则 DSL、DTO | 核心领域分支覆盖 ≥90% |
| 数据库测试 | PostgreSQL 18、迁移、约束、RLS、并发 | 不使用 SQLite 替代 |
| API/契约 | OpenAPI、RFC 9457、幂等、分页、向后兼容 | 全部 P0 路径通过 |
| 集成测试 | API + Worker + Redis + MinIO + Mailpit + Agent Mock | P0 闭环通过 |
| APP 组件/E2E | 页面状态、弱网、权限、上传、会话恢复 | Android/iOS 真机 |
| 安全测试 | 越权、Token 轮换、签名 URL、限流、日志脱敏 | 0 个阻断/高危 |
| 恢复测试 | PostgreSQL PITR、对象恢复、删除账本重放 | 达到 RPO/RTO |

## 2. 固定测试数据

仅使用可重复生成的合成患者 A/B、合成 PDF/图片与 Agent 响应。数据集包含正常、空值、边界、冲突、不可读文件、恶意 MIME、迟到回调和跨患者引用。真实患者数据不得进入 CI、截图或缺陷附件。

## 3. P0 场景

1. 邮箱注册、验证、登录、刷新轮换、退出、密码重置和全部会话撤销。
2. 患者 A 无法通过 ID、下载 URL、任务/证据引用读取患者 B 数据。
3. 上传三步流程、MIME/文件头/大小校验、失败补偿和删除。
4. 五类健康记录 CRUD、乐观锁、软删除和版本证据。
5. 模型候选确认前不进入事实视图，纠正后生成新版本。
6. 用药双状态、重复日程与未回应保持 `pending`。
7. 规则引擎在智能体关闭时仍运行；`test_only` 规则无法生产加载。
8. Worker 唯一 claim；派发重试、重复回调、迟到回调、部分成功和死信均幂等。
9. 删除后新任务不含源记录，历史证据不显示原文；账号注销完成链路。
10. Redis 清空不丢权威状态，备份恢复后删除账本重放。

### F01 认证闭环补充验收（ADR-0007）

| 编号 | 场景 | 预期 |
|---|---|---|
| T01 | 注册、邮箱验证、登录、refresh rotation、退出、密码重置 | 重置邮件请求不枚举账户；确认令牌单次有效且撤销全部会话 |
| T01a | 不存在邮箱、错误密码、未验证账户尝试登录 | 全部为同一 `401 INVALID_CREDENTIALS`，响应不暴露账户状态 |
| T01b | 已轮换 refresh token 并发/重放（控制交错：首请求持有根锁并提交轮换，第二请求随后取得根锁并重读旧 token） | 旧令牌重放返回 401，并撤销该 token family 的所有有效后继；Fake DB 按 family 独立锁，PostgreSQL 集成验证 READ COMMITTED |
| T01c | 注册缺失/拒绝 health data processing 同意 | 不创建 account/profile，不写入 birth_year |
| T01d | 注册明确同意健康数据处理 | privacy_policy 与 health_data_processing 分别写入独立版本化同意记录 |
| T49 | 获取/更新本人 `/patients/me`，使用过期 profile_version 或伪造 patient_id | 仅返回当前 token 用户资料；只应用显式 PATCH 字段；旧版本 409，客户端 patient_id 被拒；甲乙资料互不可见/不可改 |
| T50 | POST `/patients/me/consents` 授予及撤回四种允许类型 | privacy_policy 被拒绝；每次追加历史；服务端只接受当前配置版本并绑定类型独立摘要哈希；跨患者只写当前 profile |
| T51 | POST `/patients/me/account-deletion` | 未认证返回 401；认证请求 202；同一领域请求复用 operation ID；账户立即 deactivated、全部 refresh session 撤销，旧 access token 失效 |

### PostgreSQL 18 F01 集成门禁

`scripts/test-integration.ps1` 仅允许连接数据库名精确为 `gutcare_business_test` 的 PostgreSQL 18.x，并分别要求 `gutcare_app` 与 `gutcare_migrator` URL。测试开始时会在该专用测试库中执行 Alembic downgrade base 后 upgrade head，因此不得指向共享或生产数据库。`compose.integration.yaml` 提供临时文件系统中的隔离实例，不创建或删除持久卷。

真实数据库用例先检查指定测试库、PostgreSQL 18.x、应用角色与迁移角色的基础属性，再由 `gutcare_migrator` 执行 Alembic downgrade base 后 upgrade heads；迁移完成后才检查新建的 `iam`/`health`/`safety` schema、应用角色表所有权与 DDL 权限、迁移角色表所有权，并逐项比对全部 heads。`gutcare_app` 与 `gutcare_migrator` 均须非超级用户且无 `BYPASSRLS`；应用角色不得拥有业务表或数据库/schema DDL 权限，迁移角色拥有迁移生成的业务表且具备受限 DDL 权限。测试还真实触发 CHECK、FK、UNIQUE 约束失败，验证甲乙患者 RLS 隔离和事务本地 `app.user_id`/`app.patient_id` 在连接复用时清理、F03–F05 的 FORCE RLS/复合归属 FK、幂等键并发语义、风险规则审核门禁、并发 PATCH 只允许一个旧版本写入成功、refresh 同族并发重放撤销胜出后继，以及注销事务原子性。

## 4. 非功能基线

- P0 普通 API 在本地验收数据集下 P95 ≤500 ms（不含上传与智能推理）。
- 创建分析任务 P95 ≤800 ms，异步返回 `202`，不等待模型。
- 列表默认 20、最大 100；所有测试设置超时，不允许无限等待。
- 无障碍：动态字号、读屏标签、颜色不作为唯一信息、高风险提示可聚焦。
