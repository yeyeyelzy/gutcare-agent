# GutCare Agent — 消化道疾病智能健康管理与随访系统

## 详细功能设计说明书（V1.3）

> 文档类型：功能需求与业务流程设计（仅包含功能层面的设计，不含技术栈、竞赛评分、开发排期）
> 用户角色：**患者**（唯一业务角色），系统支持**多个相互隔离的患者账户**
> 目标场景：已由医疗机构确诊、需要在院外管理饮食、排便、症状、服药和活动情况的消化道疾病患者
> 首期重点验证人群：已确诊的成年肠易激综合征（IBS）患者；其他消化道疾病可使用通用记录功能，但不自动宣称具有同等疾病专属建议能力
> 版本：V1.2 · 2026-10-16（新增 F14 心情记录；认证维持邮箱+密码）

## 0. 阅读说明与功能边界

### 0.1 需求优先级

- **P0 — 核心闭环**：作为可运行系统的基本功能，应优先实现并进行端到端验证。
- **P1 — 增强体验**：与核心功能有关，条件允许时实现；不应妨碍 P0 稳定性。
- **P2 — 后续扩展**：纳入系统规划，本版本不作必须完成的承诺。

### 0.2 系统承担与不承担的职责

**系统承担：**

1. 帮助患者保存、检索和核对医疗资料与日常记录。
2. 借助图像、文本理解能力辅助结构化整理饮食和排便记录。
3. 将**已确认的诊断及医嘱**与长期饮食、症状、排便、心情和用药打卡数据联系起来，发现值得关注的变化与时间关联；心情必须获得专项智能共享授权。
4. 提供带有证据来源的健康生活建议、记录提醒与异常症状就医提示。
5. 允许患者修正 AI 识别结果、查看历史建议及其依据，控制本人数据。

**系统不承担：**

1. 不根据粪便照片、饮食照片或聊天内容独立确诊疾病。
2. 不对临床急症做确定性预测，不把模型置信度当成真实医学风险概率。
3. 不自动决定停药、换药、加减剂量，不覆盖医院处方与医嘱。
4. 不承诺持续监护、急救响应或医院的实时介入。
5. 不强制患者上传敏感图像；应提供文字和手动选择替代路径。
6. 心情记录仅反映患者主观自述，不诊断心理/精神疾病，不宣称提供危机监护或心理治疗，也不将时间关联表述为因果。

> **业务原则：患者确认的信息与其提供的原始医嘱优先于模型推断；高风险症状使用经审核的明确规则优先分流；资料不足时允许不作判断。**

### 0.3 用户角色与账户边界

仅设置**患者**一种业务角色：

- 患者甲和患者乙分别注册、登录、记录和查看自己的内容。
- 一个患者账户对应一个主体健康档案；不设计医护端、医院端或管理员业务角色。
- 后台服务中的智能体、任务处理组件和安全规则并不是产品用户角色。
- 即使患者主动猜测另一个用户的记录编号，也不能读取、修改或删除他人的记录。

### 0.4 全局设计约定

| 约定 | 具体规则 |
|---|---|
| 数据来源 | 区分“患者手动填写”“患者确认”“报告原文抽取”“AI 推断”四种来源 |
| 时间 | 保存事件发生时间与记录创建时间；允许补录历史；正确处理跨日记录 |
| 患者更正 | AI 识别结果可修改，原图与更正记录保留关联；更正后的确认值用于后续分析 |
| 分析版本 | 一份建议关联生成时使用的档案和记录版本；后续修改不能悄悄改写历史建议 |
| 医疗结论 | 对观察、关联、推测和已确诊信息使用不同标识，不将关联写成因果 |
| 资料缺失 | 展示“信息不足”“需要确认”，而不是补造数据 |
| 删除 | 由患者确认删除，相关历史展示与分析引用按规则失效或标记，不出现孤立数据 |
| 风险提示 | 优先展示有明确依据的就医建议，紧急危险征象不等待大模型任务完成 |
| 数据权限 | 所有读取、编辑、分析、导出均只作用于当前登录患者的授权数据 |

## 1. 患者端整体页面与功能导航

### 1.1 页面结构

| 一级页面 | 二级页面/区域 | 主要操作 | 优先级 |
|---|---|---|---|
| 首页 | 今日概览 | 查看最新建议、待打卡事项、近期记录、未读风险提示 | P0 |
| 我的档案 | 基本信息、疾病信息、医疗文件、用药计划 | 录入、上传、核对、编辑与归档 | P0 |
| 健康记录 | 饮食、排便、症状、服药、运动、心情 | 新增记录、查看列表、修改与删除 | 饮食/排便/症状/服药/心情 P0；运动 P1 |
| 智能分析 | 单条分析、综合分析、任务历史 | 发起分析、查看状态与结果、重新分析 | P0 |
| 我的建议 | 建议卡片、建议历史、反馈 | 阅读依据、标记有帮助/无帮助、查看变更 | P0；反馈 P1 |
| 风险提示 | 提示列表、详情、确认查看 | 查看风险原因和就医建议 | P0 |
| 健康趋势 | 时间轴、统计图、周期摘要 | 切换日期范围、筛选指标、查看来源记录 | P1 |
| 个人设置 | 隐私授权、通知偏好、数据导出/删除 | 管理本人账户及数据 | 基础设置 P0；导出 P1 |

### 1.2 首页信息顺序

从上到下建议展示：

1. **重要风险提示区域**：存在未读紧急提醒时优先展示；没有时不占用大面积空间。
2. **今日记录进度**：饮食、排便、症状、服药；无用药计划时不出现“漏服”提示。
3. **最新综合建议摘要**：显示生成时间、覆盖时间段、来源信息是否已更新。
4. **快速记录入口**：拍照记饮食、记排便、记症状、服药打卡。
5. **近期趋势摘要**：仅显示有足够有效记录的趋势；数据不足则引导记录。

首页数字均可点击进入对应记录明细，不设计无法解释的“综合健康分数”。

### 1.3 全局交互状态

主要页面应统一具备：加载中、成功、无数据、无权限、失败及可重试等状态。上传、解析、分析是不同阶段，不能将“文件已上传”直接显示为“智能分析完成”。

## 2. F01 患者账户与基本资料管理

**目标：** 让患者能够安全地保存本人数据，并在不同会话中持续使用。
**优先级：** P0

### 2.1 注册、登录、退出

**操作：**

1. 患者进入注册页面，分别确认隐私说明和健康数据处理单独同意（展示对应版本）；未同意健康数据处理时不采集出生年份、不创建患者资料。
2. 登录后进入本人首页；未登录用户不得直接打开个人医疗记录地址。
3. 可正常退出；退出后通过系统返回、任务切换或重新打开 APP 均不得再次展示受保护内容。
4. 登录状态到期时提示重新登录，允许在重新认证后恢复未完成的非敏感表单草稿（可选）。

**基础字段：** 账户标识、登录凭据、账号创建时间、最后登录时间、用户协议/隐私授权状态。

**异常要求：** 注册与登录仅提供邮箱+密码；手机号/SMS 不是本期认证方式。重复账户、错误凭据、邮箱未验证和会话过期时展示不泄露账户状态的提示；限制异常高频登录尝试。依据 ADR-0007，登录失败统一为 `401 INVALID_CREDENTIALS`。APP 不得展示手机号登录选项或接受手机号作为登录标识。

密码重置通过 `/auth/password/reset/request` 与 `/auth/password/reset/confirm` 完成。request 对邮箱是否存在均返回相同 `202`；确认令牌单次使用，重置成功撤销该账户全部刷新会话。

### 2.2 基本健康资料

| 字段 | 是否必填 | 说明 |
|---|---|---|
| 昵称 | 否 | 页面显示；为空时使用“GutCare 用户”等系统占位，不要求真实姓名 |
| 出生年份 | 是 | P0 仅收集四位年份，用于年龄段与适用范围判断；不收集完整出生日期或身份证号 |
| 已确诊疾病 | 条件必填 | 发起疾病专属建议前需存在已确认的诊断信息 |
| 诊断日期 | 否 | 允许未知，不能自动猜测 |
| 主要随访目标 | 否 | 如记录腹胀、排便规律、饮食反应等 |
| 其他影响建议的限制信息 | 自愿 | 如患者主动填写的特殊饮食限制；须明确来源与确认状态 |

**要求：** 不必一次填写所有字段；缺少关键医疗背景时允许记录生活信息，但综合建议须降低个性化程度并提示信息不足。

资料修改通过 `/patients/me` PATCH 携带当前 `profile_version`；仅修改显式提交字段，昵称允许 `null` 清空，版本冲突时要求重新获取后再提交。`privacy_policy` 不通过通用授权接口撤回；撤回基础服务条款同意时应进入专用账号注销流程。

### 2.3 验收标准

- A01：账户甲、乙分别新建相同日期的饮食记录，甲只能查看自己的记录。
- A02：退出后直接访问此前的报告详情地址，系统要求重新登录。
- A03：档案信息未完善时，仍可添加饮食/症状记录，疾病专属建议显示适用性限制。

## 3. F02 医疗档案与诊断报告管理

**目标：** 从“报告文件存储”升级为“具有来源、时间和确认状态的动态患者医疗档案”。
**优先级：** P0

### 3.1 医疗报告上传

**支持的资料类别：** 门诊病历、出院小结、诊断证明、检查检验报告、处方或医嘱单、其他相关资料。

**患者操作流程：**

1. 选择文件类型，上传 PDF/JPG/PNG 等支持格式。
2. 填写或确认报告日期、就诊机构（可选）、备注。
3. 查看上传成功结果；系统创建“待解析”任务。
4. 文件解析后展示提取结果与原文对照区域。
5. 患者核对、补充或更正，并主动点击“确认加入档案”。

**文件字段：** `document_id`、`patient_id`、`document_type`、`visit_date`、`upload_time`、`filename`、`file_status`、`parse_status`、`confirm_status`、`file_reference`。

**输入限制：** 前端显示文件格式、最大体积及张数限制；实际数值由实现时配置。损坏、加密、无法读取或清晰度不足的文件要反馈原因，允许重新上传。

### 3.2 报告智能解析与患者核对

| 解析目标 | 建议保存字段 | 处理要求 |
|---|---|---|
| 疾病与诊断信息 | 疾病名称、原文片段、报告日期 | 区分“明确诊断”“疑似/待排”“既往史”，不得把疑似直接转成确诊 |
| 医生建议 | 医嘱内容、适用时间、来源 | 保留原文，不在解析阶段擅自改写成新的医嘱 |
| 检查结果 | 项目、结果值、单位、参考范围、日期 | 原文缺失单位时不可自造；异常解释应由合适规则和知识支持 |
| 药物信息 | 药品名称、剂量、频率、疗程、用法 | 字段缺失显示待补充，不推算剂量 |
| 其他信息 | 过敏/特殊限制（若原文包含） | 高影响字段要求患者确认 |

**界面要求：**

- 左侧显示报告原始页/图片，右侧显示可编辑抽取字段。
- 对低可信、识别失败和冲突字段进行显著标识。
- 每个已确认字段可追溯到文件与所在页/原文片段（能够定位时）。
- 允许选择“仅保存文件，不加入医疗档案”。

### 3.3 动态档案更新与冲突处理

例如两份报告具有不同诊断日期、治疗方案或医生建议时：

1. 按报告时间保存历史版本，不直接覆盖旧报告。
2. 系统列出差异，提示患者确认当前有效的医嘱或用药方案。
3. 对无法确定是否仍有效的旧用药信息，标记“状态待确认”。
4. 下游建议只使用明确有效或已确认的医疗背景；有冲突时提示患者核对医生意见。
5. 如果新报告已确认，旧建议标记“依据已更新，可重新分析”，不悄悄修改原建议内容。

### 3.4 报告管理操作

支持列表、时间排序、类型筛选、查看原文件、查看解析结果、编辑确认字段、删除（需二次确认）。删除报告时须提示其衍生字段及历史建议的关联影响。

### 3.5 异常与验收

- A04：上传模糊扫描报告，系统允许标记“解析不充分”而非生成虚构诊断。
- A05：解析出的药品名称被患者更正后，新分析使用更正值，历史抽取结果留有记录。
- A06：一份报告中出现“考虑某疾病”，默认不得进入“已确诊疾病”字段。
- A07（ADR-0018）：仅对患者确认的 `test_item` 与 `test_result` 保守生成跨报告待核对冲突；同患者、不同文档、规范化项目/单位/有效采样日一致且结果不同才构成候选。有效日优先采样日，缺失回退文档日期；不同日期是趋势，不是冲突。患者可显式选择 `keep_both`，服务不自动择优。开放冲突在 F08 快照中作为 `unresolved` envelope 投影，不再重复列为普通事实；诊断、建议和用药文本语义/相互作用不自动比较。

## 4. F03 饮食记录与饮食分析

**目标：** 记录患者真实饮食事件，为后续与症状、排便情况的时间关联提供数据。
**优先级：** P0

### 4.1 新增饮食记录

**输入方式：** 文字快速记录、上传食物图片、文字与图片结合。应允许不拍照直接保存。

| 字段 | 必填性 | 说明 |
|---|---|---|
| 用餐日期与时间 | 必填 | 默认为当前时间，可选择历史时间 |
| 餐次 | 推荐 | 早餐/午餐/晚餐/加餐/其他，可改选 |
| 食物名称或描述 | 至少一种有效内容 | 手工输入或通过图片识别并确认 |
| 图片 | 可选 | 可上传多张，但不可要求患者必须上传 |
| 份量 | 可选 | 可描述为少量/适中/较多或自定义，不强制填写克数 |
| 烹饪方式 | 可选 | 煎炸、蒸煮等，未提供时不能自动认定 |
| 主观感受/备注 | 可选 | 如饭后饱胀等；也可链接独立症状记录 |

**流程：**

1. 患者先创建饮食记录，可不带图片。
2. 患者可将最多 10 张已安全上传的饮食图片关联到该记录；附件集合独立于记录 CRUD 版本化。
3. 患者查看本次饮食识别披露并再次确认后，才创建独立图像识别请求；任务仅使用本记录当时的附件集合。
4. 按 Agent 显式返回的 request-local opaque `candidate_group_key` 将同一食物项的跨图片字段分组；不按名称相似度、类别或图片位置自动合并。Diet 仅展示名称、受控类别和粗略份量三类候选，患者仍须逐字段 accept/edit/reject。
5. `food_name` accept/edit 才创建含非空名称的确认食物项；创建事务分配稳定 `item_position`。同组类别/份量只能在名称已确认后分别决定，先操作返回 409 `candidate_dependency_unmet`，候选保持待确认且不创建部分记录。份量确认写入 `DietItem.amount_text`。拒绝名称不产生事实，并使同组其余待决字段失效/清敏感值；拒绝其他字段只拒绝该字段。
6. 患者可随时手动新增、编辑或删除食物；Agent 不可用、图片无法识别或授权缺失均不阻断手动记录。重试使用新 request/group，不与旧 request 或既有食物项自动合并。
7. 系统可提示“是否记录餐后不适”，但不得默认判定出现不适。

### 4.2 图片识别范围

**可尝试识别：** 食物名称、受控食物类别和粗略份量描述。图像识别不输出烹饪方式；烹饪方式仅可由患者手工输入。
**不得直接断言：** 精确热量、精准营养素克数、不可见的添加剂、食材过敏原、隐藏调味料或对该患者必然有害。

多食物混合、光线不足、图片无法确定成分时，要有“未识别/请补充”状态。每个饮食候选字段都必须携带 UUID group key；同一 key 可由 Agent 明确用于不同附件上的同一食物项，不同组、附件或 request 不可由业务端按内容猜测合并。相同 request/group/type 只能有一个字段候选。患者确认的食品名称是后续分析的主要依据。

图像能力不估算精确卡路里/营养素，不猜隐藏食材或过敏原，不给出诊断、风险或因果判断。候选在逐项确认前不进入记录明细、趋势、风险规则或综合分析。

### 4.3 单餐分析

展示“记录内容摘要”，例如：

- 本餐已确认的食物类别。
- 可能与患者既有记录相关、值得继续观察的饮食特征。
- 支持本次提示的具体记录及医学知识依据（如有）。
- 不确定性和缺失信息，例如调味料或份量未知。

**不宜在一餐记录后直接判定某种食物引发疾病。** 单次分析主要服务于数据结构化和记录反馈。

### 4.4 饮食历史与修改

- 以日期或餐次查看历史记录，支持补录和修改。
- 修改已用于综合分析的旧记录后，新分析按最新确认内容运行；旧分析保留其当时数据版本。
- 一条餐次可与多条症状记录按时间关联，但不直接建立因果结论。

### 4.5 验收标准

- A08：无图片、仅输入“米饭、蔬菜”也能保存饮食记录。
- A09：图片识别错误时，患者修改食物名称后保存；建议依据中引用的是确认后的食物。
- A10：模糊图片不应阻断文字手动记录；系统不生成未经依据支持的精确热量。
- A11：患者修改昨天的餐次后，重新分析可读取新版本，历史建议标记依据过时。

## 5. F04 排便与粪便记录分析

**目标：** 以患者主动记录为主、图像辅助为辅，整理长期排便模式。
**优先级：** P0

### 5.1 新增排便记录

| 字段 | 必填性 | 说明 |
|---|---|---|
| 排便日期与时间 | 必填 | 支持补录 |
| Bristol 粪便类型 | 推荐 | 可手动选择 1—7 型；未确定时允许“无法判断” |
| 粪便图片 | 可选 | 每条记录最多一张；明确说明敏感图片、处理目的、已披露第三方及短时访问；上传前可取消 |
| 排便量感受 | 可选 | 少/一般/多/不确定 |
| 排便过程感受 | 可选 | 费力、排不尽感、排便急迫等 |
| 颜色/可见特征 | 可选 | 应优先由患者描述，不依靠照片作出出血诊断 |
| 同时出现的症状 | 可选 | 可跳转新增腹痛、腹胀等症状记录 |
| 备注 | 可选 | 自由输入，提示避免暴露无关隐私 |

### 5.2 图像辅助分析

**处理流程：**

1. 患者将最多一张已安全上传图片关联到排便记录。
2. 患者查看本次排便图片识别披露并再次确认，创建独立于 F08 的识别任务。
3. Agent 仅可给出图像质量和可能的 Bristol 1–7 候选；不返回中性可见形态、visual tag 或 diet group key。图像不足时返回无法识别。
4. 患者可接受、编辑或拒绝 Bristol 候选；仅 Bristol 被确认/编辑后写入患者确认字段。手工排便 CRUD 不依赖任务成功。
5. 图片能力仅对该任务短时有效，图片或记录删除、版本变化、授权撤回会关闭能力并使待确认候选失效。

系统不得只根据颜色或图像自动确认“消化道出血”“炎症”“癌症”等诊断。若患者主动报告黑色柏油样便、明显便血等危险征象，应进入独立的风险分流流程。

模型不得从图像判断/推断出血、疾病、诊断、严重性或风险，也不得改变 F10 确定性规则。排便图片识别不输出病理/因果解释。

### 5.3 排便趋势统计

- 统计按日/周的排便次数、Bristol 类型分布与异常记录频次。
- 允许一日多次排便，每次独立存档。
- 时间段无记录应显示“未记录”，**不能等同于没有排便**。
- 可以与症状时间线联合展示，但必须保留患者手动确认与模型推断的区别。

### 5.4 验收标准

- A12：没有上传照片仍能手动选择 Bristol 类型并保存。
- A13：上传无法识别的图片时，记录可手动完成，显示图像分析未成功。
- A14：同一天记录三次排便，周统计计入三次，不被覆盖为一次。
- A15：连续两天没有记录时，页面显示“无数据”，而不是“未排便”。

## 6. F05 消化道症状记录

**目标：** 将饮食与排便之外的主观症状独立记录，为安全提示和长期变化分析提供关键信息。
**优先级：** P0

### 6.1 症状种类与输入

**预设类别：** 腹痛、腹胀、腹泻、便秘、恶心、呕吐、反酸、食欲变化、便血相关主诉、其他。

| 字段 | 必填性 | 说明 |
|---|---|---|
| 症状类型 | 必填 | 支持多选或一次记录一个主要症状 |
| 发生时间 | 必填 | 可以选择现在或历史时间 |
| 严重程度 | 推荐 | 使用统一主观刻度，例如 0—10 分，并解释“患者主观感受” |
| 持续时间 | 可选 | 不知道时允许为空 |
| 位置与表现 | 可选 | 如腹部位置、阵发或持续等 |
| 伴随情况 | 可选 | 可记录呕吐、发热、明显便血等经患者确认的表现 |
| 与饮食或排便的关联 | 可选 | 选择某条已存在记录，而非强行自动绑定 |
| 备注 | 可选 | 自由描述 |

### 6.2 症状记录流程

1. 患者选择症状并填写时间及严重程度。
2. 系统先执行基础输入校验和高风险症状规则检查。
3. 若命中已审核的紧急危险征象，直接展示就医提示，不等待综合 Agent 完成。
4. 常规症状保存后进入历史时间轴，可用于后续综合分析。
5. 用户可以补充“症状已缓解”或“症状仍持续”，系统保留更新历史。

### 6.3 关键限制

- 严重程度的自评分数不单独等于疾病风险等级。
- 同一症状类别在不同疾病背景下可能意义不同，应结合已确认档案和审核后的规则处理。
- 无法确认症状的发生时间时，允许保存为“时间不详”，但不参与需要精确先后关系的分析。

### 6.4 验收标准

- A16：患者输入明确的危险征象时，页面即时出现就医提示，且保留记录。
- A17：症状未填写持续时间时仍可保存，但分析标注信息缺失。
- A18：用户修改症状发生时间后，后续时间关联结果使用新时间。

## 7. F06 服药计划、打卡与提醒

**目标：** 帮助患者按**已有处方或确认的用药计划**记录服药，不提供新的处方决策。
**优先级：** P0

### 7.1 服药计划管理

| 字段 | 必填性 | 说明 |
|---|---|---|
| 药品名称 | 必填 | 由患者填写，或从处方中抽取后确认 |
| 单次剂量与单位 | 条件必填 | 已知则按处方原文录入，不推断未知剂量 |
| 服用频率 | 条件必填 | 仅在明确计划时用于提醒与打卡 |
| 计划开始/结束时间 | 可选 | 无明确疗程时可为空 |
| 服药时间点 | 可选 | 可配置每日多个时间点 |
| 来源 | 必填 | 医院处方、患者手动填写等 |
| 确认状态 | 必填 | 待确认/已确认/需复核；表示来源信息是否经患者确认 |
| 执行状态 | 必填 | 使用中/已结束/已停用；表示计划的业务生命周期 |

ADR-0010 补充冻结：来源仅为患者手动录入或同患者医疗档案；来源文档软删除不删除计划历史。确认状态与计划生命周期独立；`pending` 打卡只表示尚未回应，不能推断为未服用。重复日程、时区/DST 和变更历史按 ADR-0010 执行。

**操作流程：** 读取已有处方信息 → 提供待确认计划 → 患者核对 → 激活用药计划 → 展示待打卡项。

### 7.2 服药打卡

每次计划服药产生一个可查看的事件：

- 已服用：患者主动确认，并记录实际服用时间（可补录）。
- 未服用：患者主动选择，允许记录原因。
- 暂未确认：到时未打卡也只能视为“未确认”，**不能自动断定漏服或未服药**。
- 计划变更：由患者依据医生新处方主动更改，旧计划保留历史。

### 7.3 提醒与依从性展示

**P0：** 在应用内展示今日待打卡计划，并允许配置提醒偏好。
**P1：** 在用户授权且运行环境支持时，提供系统本地通知或移动推送提醒。
**P2：** 接入其他外部提醒渠道。

依从性统计应说明分母范围，只统计有明确计划且记录状态可判定的事件；“未确认”与“明确未服用”分别显示。

### 7.4 安全边界与验收

- A19：无处方且未确认剂量时，不主动生成具体药物剂量计划。
- A20：超过计划时间未打卡时显示“待确认”，不写成“已漏服”。
- A21：患者询问“漏服后是否加倍服药”时，系统不得擅自回答增加剂量，应提示按药品说明或咨询医生/药师。
- A22：新处方生效后旧计划归档，历史打卡数据仍可追踪。

## 8. F07 运动与活动记录

**目标：** 记录可能与日常管理有关的活动习惯，作为综合分析的辅助信息。
**优先级：** P1（基础手动录入可尽早实现）

### 8.1 字段与操作

- `occurred_at` 为活动开始时间；类型 `walking/jogging/cycling/other`，other 必须有 1–160 字描述。
- 强度 `low/moderate/high`、主观感受 `better/same/worse`、时长 1–1440 分钟。
- 添加、本人详情/列表、修改、软删除；时间过滤使用 `[since,until)`，cursor 稳定，PATCH/DELETE 使用 `record_version` 乐观锁。

### 8.2 与其他模块的联动

- 综合建议可利用运动频次、记录完整度作为辅助背景。
- 如果记录活动后明显出现不适，提示补充症状记录，而不是自动诊断原因。
- 不根据单次运动自动生成未经医生确认的康复训练处方。

### 8.3 验收标准

- A23：手动记录30分钟步行后，可在周视图正确汇总。
- A24：没有运动记录时，系统不能将其解释为患者完全没有运动。

## F14 心情记录

**目标：** 让患者自愿记录主观心情与情绪状态，供本人回顾；在单独授权有效时，将最小化的结构化心情字段纳入综合分析任务。心情记录不用于诊断心理或精神疾病，也不用于推断肠道疾病与情绪之间的因果关系。
**优先级：** P0。患者可以选择不记录；撤回心情处理或智能共享授权不阻断其他健康记录与分析。

### 记录字段与操作

| 字段 | 必填性 | 说明 |
|---|---|---|
| 记录发生时间 `occurred_at` | 必填 | 默认当前时间，允许患者补录；请求必须带时区，后端保存 UTC |
| 主观心情等级 `mood_level` | 必填 | 1–5 整数，由低到高仅表示患者当时自我评价，不映射临床量表 |
| 情绪标签 `emotion_tags` | 可选 | 从受控枚举多选，0–5 项；不允许自定义诊断标签 |
| 备注 `note` | 可选 | 最多 500 字；按高敏自由文本保护，不用于趋势、风险规则或智能体快照 |

患者可新增、列表查看、详情查看、修改和删除本人记录。新增和修改要求 `health_data_processing` 与 `mood_data_processing` 当前有效；本人读取与删除作为数据访问/删除权利，即使撤回心情处理授权后仍可用（账户冻结或注销期间依 F13 规则限制）。修改需提交当前 `record_version`；删除立即从详情、历史时间线和新分析中隐藏，按单记录 7 天清理。默认列表只返回日期、等级和受控情绪标签，不在通知、推送或埋点展示备注。

情绪标签稳定码为 `calm`、`content`、`joyful`、`sad`、`anxious`、`irritable`、`overwhelmed`、`tired`、`other`。`other` 只表示未列出的主观情绪，不接收附加自由文本；未知枚举、重复标签或超过 5 项返回 422。

### 单独授权与分析边界

心情数据属于高敏健康信息。新增和修改要求当前有效的 `health_data_processing` 与 `mood_data_processing` 单独同意；将心情数据交由智能体处理还要求 `mood_ai_sharing` 与 `third_party_ai` 均有效。本人读取与删除保留为数据主体权利，不因撤回授权而关闭；其他健康数据的分析不因缺少心情授权而失败。

任务快照仅可含 `mood_level`、受控 `emotion_tags`、发生时间、记录 ID/版本和受控来源 locator；不得包含 `note`、原始模型输出或从附近记录构造的心理状态。撤回任一心情授权后，拒绝创建含心情的后续快照，并在任务授权栅栏内取消未完成且含心情输入的任务；重试不得绕过授权重新读取。

分析结果只能描述记录中可观察到的时间关联与不确定性，不得称情绪导致肠道症状、判定心理疾病、进行心理危机诊断或提供治疗建议。患者主动表达自伤等危机内容不属于本模块规则判定范围；产品不得暗示本模块提供危机监护服务。

### 验收标准

- A46：未授予 mood_data_processing 时拒绝新增/修改心情记录并返回 RFC 9457 `CONSENT_REQUIRED`；本人读取/删除及其他功能仍可使用。
- A47：撤回 mood_ai_sharing 后仍可新增、修改和查看心情（mood_data_processing 仍有效），但新建分析快照排除心情字段。
- A48：授权齐全时快照仅含允许的结构化心情字段；备注、日志、通知、趋势和风险规则均不包含备注内容。
- A49：时间戳、等级、情绪枚举、标签数量及未知字段在 APP/API/数据库边界一致校验；跨患者访问统一 404，旧版本修改返回 409。
- A50：删除或注销后心情记录立即不可见并排除新分析，导出按授权类别包含数据，清理 worker 在既定 SLA 内完成清除。
- A51：心情趋势按患者 IANA 时区日/周分桶，只统计 mood_level，返回每桶 has_data、记录数与五档计数；note/emotion_tags 不进入趋势，且不依赖 Agent 共享授权。
- A52：分析预览返回 `mood_record_count_in_range`、`mood_record_count_eligible`、`mood_record_count_excluded_by_consent` 与受控原因；任务 `input_summary.included_mood_record_count` 等于实际不可变快照 mood 来源数量，历史不得按当前记录重算。

## 9. F08 智能分析中心

**目标：** 基于多项已确认的患者信息形成可检查、可追溯的综合分析结果。
**优先级：** P0

### 9.1 分析类型

| 类型 | 触发方式 | 数据输入 | 输出 |
|---|---|---|---|
| 单条辅助分析 | 上传报告、饮食或粪便图片 | 单条原始文件/图片及少量补充字段 | 由 F02 或对应记录流程返回可供患者确认的结构化识别结果；不使用 F08 综合任务 |
| 综合随访分析 | 患者点击“开始综合分析” | 当前授权的已确认档案事实 + 时间范围内饮食、排便、症状、服药等结构化事实 | 观察摘要、时间关联、证据与不确定性；不创建建议实体 |
| 周期总结 | 患者选择最近7天/30天；定时生成属 P1 | 该周期内有效的历史记录 | 周期摘要、记录完整度与重要变化 |
| 重新分析 | 档案或关键记录更新后，患者主动触发 | 最新有效版本 | 新的分析结果，并关联此前版本 |

### 9.2 综合分析前的检查

1. 是否存在已确认的患者医疗背景；若无，则只可生成一般性记录摘要，并提示不能提供疾病专属建议。
2. 本次时间范围内是否有有效数据；完全为空则不运行空洞分析。
3. 哪些信息来自患者确认，哪些仍为 AI 待确认或低可信状态。
4. 是否存在冲突或已过时的用药计划，是否影响建议的适用性。
5. 有无必须先处理的高风险症状；若有，先由安全规则产生提示。

### 9.3 分析任务生命周期

| 状态 | 患者看到的内容 | 允许操作 |
|---|---|---|
| 待处理 | 已收到请求，等待分析 | 查看任务、按约束取消 |
| 分析中 | 显示阶段或简单进度，不伪造精确百分比 | 离开页面，稍后查看 |
| 待补充信息 | 缺乏必要确认信息 | 跳转相应记录进行更正 |
| 已完成 | 显示摘要、建议与依据 | 查看完整报告、再次分析 |
| 失败 | 给出可理解的失败原因 | 重试或返回记录页面 |
| 已取消 | 用户主动取消/系统确认取消 | 重新发起 |

**要求：** 同一次请求应有唯一任务编号；`POST /analysis-tasks` 必须带 `Idempotency-Key`，相同请求重放原始 202 响应，不同摘要冲突。创建时在同事务冻结 confirmed facts/records、来源版本/locator 与摘要；没有已确认可分析数据时拒绝。离开页面、切换后台或重启 APP 后可列表/查询状态。pending/processing 可取消；仅 failed 可显式重试并创建引用原冻结快照的新尝试。终态不接受迟到回调。Agent 只读任务快照并提交白名单结构化结果，业务服务校验每条 evidence 的来源/版本/locator；不保存原始 prompt 或模型输出。授权撤回或账号冻结通过患者 advisory fence 原子阻止新任务并取消已有非终态任务。F08 结果不是 F09 建议，不生成诊断、处方或药物调整结论。

### 9.4 综合分析结果组成

一份综合报告建议包含：

1. **分析范围与资料概况**：日期范围、参与的确认事实/记录数量、缺失数据。
2. **近期状态摘要**：排便模式、症状变化、饮食记录特征、服药打卡情况。
3. **可观察的时间关联**：例如部分餐次与随后症状在时间上接近，明确不能据此确定因果。
4. **潜在冲突与资料不足**：相互矛盾的已确认事实或缺失信息。
5. **风险上下文**：独立确定性安全规则产生的提示状态，分析结果不得覆盖。
6. **证据列表**：每条观察可关联到此快照中的来源记录及版本；F09 建议由后续独立功能处理。

### 9.5 验收标准

- A25：在同一个患者账户中添加新症状并重新分析，结果的输入记录范围相应变化。
- A26：不填写诊断信息而发起分析，系统限制疾病专属建议并明确说明原因。
- A27：模型超时后任务显示失败、可重试，已保存的生活记录不丢失。
- A28：相同请求重复点击不会无故产生多个重复报告或通知。
- A29：对于无来源支持的药物调整结论，结果输出校验必须拦截。

## 10. F09 个性化建议接收、管理与反馈

**目标：** 将智能分析结果变为患者能阅读、核对依据、持续使用的建议，而非一次性的聊天回复。
**优先级：** P0；反馈能力 P1

### 10.1 建议卡片内容

| 字段 | 含义 |
|---|---|
| 建议标题 | 简短可读，如“继续观察某类饮食与腹胀记录” |
| 建议类型 | 饮食、生活方式、记录管理、用药打卡、就医咨询 |
| 建议正文 | 患者容易理解、具体但不过度确定的行动提示 |
| 适用前提 | 采用了何种已确认诊断和数据范围 |
| 证据引用 | 关联报告、餐次、排便、症状及知识资料的编号或入口 |
| 不确定性说明 | 样本太少、时间不详、照片不清楚等 |
| 生成时间 | 说明这是哪次分析的结果 |
| 状态 | 新建议、已读、依据已更新、已归档 |

### 10.2 建议生成的业务约束

- 不直接开立处方、安排药物剂量或否定已有医嘱。
- 禁止使用“某食物一定导致疾病”“图片证明患有某病”等绝对表述。
- 记录不足时建议继续收集数据，而不是输出不真实的个性化结论。
- 不应把患者从未输入的症状当成已发生事实。
- 若缺乏合适的专业知识支持，明确显示“暂不提供该疾病的专属建议”。
- 风险规则认定需要立即就医时，不能给出延误就医的普通饮食建议作为替代。

### 10.3 建议阅读与反馈

**患者可执行：**

1. 在首页查看最新建议摘要，点击进入详情。
2. 查看建议依据，回跳到原报告或原健康记录。
3. 将建议标记为“已读”；查看历史版本。
4. （P1）反馈“有帮助/无帮助/不适用”，可以填写原因。
5. （P1）将建议加入“待跟踪事项”，在后续记录中自愿反馈执行情况。

反馈用于优化展示和随访关注，不应未经验证直接变成临床效果数据。

ADR-0013 补充冻结：F08 的分析结果与 F09 建议是不同实体。建议仅由独立受限 callback 提交，必须关联 `succeeded/partial` F08 task；患者可通过 `/advice` 列表/详情、`/{id}/read`、`/{id}/archive` 和 `/{id}/feedback` 管理。建议生命周期为 `new/read/archived`，`basis_updated` 独立展示。患者证据仅来自同任务快照的精确来源引用；知识证据仅含可版本化引用 metadata，不收录原文。F10 风险提示优先展示，建议不得关闭、降级或延迟风险处置。

### 10.4 验收标准

- A30：点击建议的“依据”能定位到所属患者的具体输入记录。
- A31：更改源数据后旧建议仍可查看，但清楚标记“生成依据不是最新版本”。
- A32：资料缺失时系统输出“无法给出疾病专属建议”，而不是编造。

## 11. F10 异常症状检测与风险提示

**目标：** 识别患者主动记录的危险征象，根据经过审核的规则给出适当的就医提示。
**优先级：** P0

### 11.1 功能定位与安全声明

本模块应命名为“**异常症状与就医提示**”或“风险提示”，避免宣称已具备重大疾病预测或医学急救监测能力。规则必须由具有适当专业资格的人员审核后才能用于真实用户；未审核的规则仅可用于带有明确标记的竞赛模拟演示。

### 11.2 风险检测来源

- 患者症状表单中明确填写的表现。
- 排便记录中患者主动确认的相关异常表现。
- 既往医疗档案中已经确认的、适用于相关提示的限制条件。
- 患者提交的自由文本：可由模型辅助提取**候选症状**，但未确认的抽取结果不能伪装成确定医学事实；明显的紧急求助表述应优先展示一般性立即就医指引。

**重要：** 不依赖粪便图片单独确认出血，也不能依靠普通大模型生成的“危险概率”直接分流。

### 11.3 三级提示策略

| 提示级别 | 典型产品行为 | 限制 |
|---|---|---|
| 一般关注 | 引导补充记录、查看变化 | 仅作为记录管理提示 |
| 建议及时就医评估 | 提醒联系医疗机构，显示触发的已审核症状规则 | 不声称已诊断病因 |
| 紧急危险征象 | 页面优先提示立即寻求急诊/当地紧急医疗帮助 | 不等待 Agent、不以普通建议取代就医 |

危险征象的具体组合条件、适用疾病、例外与文案，必须单独维护经审核的规则清单。本说明书仅规定功能，不臆造临床阈值。

### 11.4 提示卡片的必备字段

`alert_id`、`trigger_time`、`trigger_record_ids`、`rule_id`、`rule_version`、`severity_level`、`message`、`recommended_action`、`read_status`、`acknowledged_at`。

**患者交互：**

1. 触发时显示就医建议与相关原因。
2. 患者点击“已查看”后，只更新已读状态，不代表症状消失或风险解除。
3. 可跳转查看触发的原始记录及提示依据。
4. 纠正误填信息后可重新评估，并保留原提醒的历史记录及更正原因。
5. 对重复触发的同一事件进行合并或去重，不反复轰炸用户；新的危险事件不能被旧的已读状态吞掉。

### 11.5 验收标准

- A33：模拟输入经测试规则指定的危险征象后，在综合分析未运行时也能展示风险提示。
- A34：点击“已查看”后，提示历史仍保留且不自动变为“已安全”。
- A35：模型分析服务故障时，已部署的确定性安全规则仍可以独立工作。
- A36：同一事件重复提交时不会产生大量重复通知；新的事件仍能产生新提示。

## 12. F11 健康趋势、周期总结与历史回顾

**目标：** 展示纵向变化而不是孤立的一次性分析。
**优先级：** P1（基础历史查询 P0）

### 12.1 历史时间线

按时间混合展示饮食、排便、症状、服药打卡、运动与建议事件，可按类别筛选。游标稳定排序为 `(occurred_at DESC, type ASC, id ASC)` 并使用 HMAC 签名；事件携带受控来源 target 供跳转，不复制来源正文。

### 12.2 统计与图表

| 图表/指标 | 数据来源 | 展示原则 |
|---|---|---|
| 每日/每周排便次数 | 排便记录 | 无记录显示缺失，不等于零次排便 |
| Bristol 类型分布 | 已确认排便类型 | 未确认/无法识别单独计数 |
| 症状严重程度趋势 | 主观症状记录 | 明确为患者自评，不是客观疾病指标 |
| 饮食类别分布 | 已确认饮食记录 | 不推导未知营养素含量 |
| 服药打卡情况 | 有效服药计划及确认事件 | “未确认”与“已明确未服”区分 |
| 活动次数与时长 | 运动记录 | 无记录不等同于没有运动 |
| 心情等级分布 | 心情记录的结构化 `mood_level` | 按患者时区日/周桶显示等级计数；仅供患者回顾，不作为临床量表、诊断或因果结论 |
| 服药打卡情况 | 有效服药计划及确认事件 | pending/taken/not_taken/skipped 分开统计 |

聚合范围采用带时区的 UTC 半开区间 `[from,to)`；按患者资料 IANA 时区计算日/周桶。既有指标只返回有数据桶；心情分桶固定返回每桶 `has_data`、`record_count` 和 `mood_level_counts`（等级 1–5；无记录时为 false、0 和五档零计数），避免零记录与缺数据混淆。心情趋势只读患者本人未删除记录的结构化等级，备注和受控情绪标签不参与聚合，且不要求 Agent 共享授权。趋势通过 SQL 聚合，不生成智能摘要；饮食、症状和心情均不作因果结论。

### 12.3 周期健康总结

患者手动选择最近7天、30天或自定义日期区间的周期总结继续复用 F08 periodic_summary 任务；F11 趋势接口不生成摘要文本。

周期报告应包含“共记录了多少天、缺失多少天”等记录完整度说明，防止少量数据形成夸大结论。支持点击图表返回原记录。

### 12.4 验收标准

- A37：选择7天范围时，所有统计只使用该范围的有效记录。
- A38：少量数据不足以支持趋势结论时显示“不足以判断明显变化”。
- A39：点击某一异常排便点能够跳转到对应原记录。

## 13. F12 站内消息、通知与任务提醒

**目标：** 让患者及时收到已经产生的分析结果、待确认事项和风险提示。
**优先级：** P0（站内）；本阶段不实现外部 push 或供应商 SDK。

### 13.1 站内通知类型

1. F08 综合分析成功、部分成功或失败。
2. F09 新建议。
3. F10 新风险提示。
4. F06 新建 pending 打卡实例的普通提醒。

### 13.2 消息行为

- 首页显示未读数量；通知列表支持稳定 cursor、类别/未读筛选、详情、单条及批量已读。
- 通知只返回类型、时间、优先级和受控 target ID，不复制正文。目标来源已删除时返回 `target_unavailable`，不泄露来源内容。
- `(patient_id, deduplication_key)` 唯一；同一 F08 终态、Advice、RiskAlert 或 schedule/local_date 只创建一次通知。
- 普通应用内提醒支持开关与可选 quiet hours；风险通知不受开关/静默时段影响，也不修改 F10 已读状态。
- 站内通知不承诺患者未打开应用时主动联系。

F06/F08/F09/F10 各自领域事务通过严格白名单 outbox 同事务生成事件；dispatcher 使用独立 `gutcare_notification_worker` 数据库角色、`SKIP LOCKED`、lease 恢复、指数退避及 dead-letter。payload 仅含事件类型、患者 ID、受控 target、时间、优先级和去重键，不含药名/剂量、正文、报告/建议内容、URL/locator、prompt 或模型原始输出。通知 API 不读取已冻结账户，注销后的通知由 F13 清理。

### 13.3 验收标准

- A40：综合分析完成后患者离开结果页仍能从通知中心找到报告。
- A41：同一任务完成事件不会产生多个重复通知。
- A42：患者关闭普通打卡提醒后，不影响自己查看风险提示列表。

## 14. F13 数据隐私、个人设置与患者自主控制

**目标：** 在唯一患者角色下，仍让用户了解哪些数据正在被记录、分析和传输。
**优先级：** P0（核心权限、全量清理与恢复重放）；P1（导出）

### 14.1 基础设置

- 修改昵称、个人基本资料和登录凭据。
- 设置应用内提醒、时间显示及普通消息偏好。
- 查看数据使用说明：医疗报告、饮食图片、粪便图片等分别用于何种分析。
- 可查看已上传文件清单，并删除不再希望保留的记录。

### 14.2 图片与敏感资料控制

- 粪便图片应明确标为敏感图像，提供不上传图片的替代方案。
- 模型处理如需使用第三方服务，应告知范围、传输方式和相应授权；未获得所需授权时不将敏感信息发送到相关服务。
- 患者删除一条源记录后，后续分析不得继续把它作为有效输入；已生成的历史结果需要保留或删除时，应给出一致、明确的策略。
- 分享和导出能力（P1）应先允许患者预览，避免包含其他无关隐私字段。

注销立即停止登录、撤销全部 consent/session、取消在途任务与导出，并创建 30 天 SLA 清理 operation。患者使用一次性 receipt 在不登录状态查询进度。对象删除前先撤销所有下载/上传/导出能力和迟到 callback，再按 F12→F09→F08→F02→F03-F07/F10→consent/profile/account 顺序清理。进度保留不关联账户的去标识墓碑。备份恢复后，清理账本重放是 readiness 前置门禁。

数据导出先按服务端类别白名单预览和确认，后台生成规范 JSON + manifest ZIP。只经同源网关发放 5 分钟一次性下载能力；能力使用后不可重放，注销和到期立即失效。导出对象进入统一 inventory 和过期清理。

### 14.3 多账户数据隔离

所有文件详情、记录检索、分析任务、建议和消息必须验证数据属于当前登录患者；不能只靠前端隐藏按钮实现权限保护。

### 14.4 验收标准

- A43：患者甲复制报告详情链接给乙，乙不能打开甲的报告。
- A44：患者取消敏感图像处理授权后，该图像不再被发送给对应分析服务。
- A45：患者删除记录后，该记录不再出现在正常查询及新分析输入中。

## 15. 多智能体的功能职责与协作约定

> 本节仅定义智能体承担的**产品功能与输入/输出责任**，不是底层工程部署架构。智能体不是独立用户角色。

### 15.1 智能体任务清单

| 单元 | 业务输入 | 业务处理 | 结构化输出 | 不能做的事 |
|---|---|---|---|---|
| Orchestrator（调度） | 用户分析请求、档案与记录概况 | 决定执行哪些分析、检查任务完成状态、合并结果 | 任务计划、执行状态、输入版本清单 | 绕过安全规则、随意读取其他患者数据 |
| Medical Agent（报告理解） | 医疗报告、确认的诊断及医嘱 | 信息抽取、识别报告日期与冲突 | 医疗背景、来源证据、待确认字段 | 将“待排”改成确诊、推断处方剂量 |
| Diet Agent（饮食分析） | 餐次图片与文字、确认结果 | 食物类别抽取、日志整理 | 结构化餐次、识别不确定性 | 无依据估算精确营养值、判断某食物必定致病 |
| Stool Agent（排便分析） | 排便图像、手动类型、症状 | 粪便外观辅助描述、排便记录整理 | 可能类型、质量评估、最终确认值 | 仅凭图片确诊疾病或出血 |
| Trend Agent（长期关联） | 有时间标记的多源记录 | 时间聚合、记录缺失标记、发现可观察的关联 | 趋势摘要、关联证据、限制说明 | 将时间相关性直接认定为因果 |
| Advice Agent（建议生成） | 确认的档案、Trend 结果、审核知识材料 | 形成患者可读的生活管理建议 | 建议项、适用条件、证据链接、不确定性 | 修改药物治疗、覆盖医生指示 |
| Safety Engine（独立规则） | 已确认的症状与相关上下文、审核规则 | 触发异常症状就医提示，校验输出 | 规则命中、提示级别、行动文案 | 依据模型主观置信度自行生成临床阈值 |

### 15.2 单条识别与综合分析的区别

**单条识别：** 上传一个报告/餐次/排便记录后，相关 Agent 只处理该条数据，生成“待患者确认”的结构化结果。
**综合分析：** 在数据确认后，由 Orchestrator 收集指定时间段，调用 Trend 和 Advice 形成跨来源结果。避免每次修改一个字符都重新执行全套分析。

### 15.3 Agent 结果共同字段

每个 Agent 的输出建议统一包含：

- `task_id`：本次分析任务编号。
- `agent_name`：输出方名称。
- `patient_id`：当前患者作用域。
- `input_record_ids`：实际使用的输入记录编号列表。
- `input_version`：所依据的记录版本。
- `observations`：观察或识别结果；区分事实、患者陈述、模型推测。
- `source_references`：原报告、原记录或审核知识的来源引用。
- `uncertainties`：低可信或无法判断的内容。
- `needs_confirmation`：是否需要患者确认。
- `status`：成功、部分成功、待确认、失败等。

**功能要求：** 上游失败时下游应知道哪些输入不可用；允许“部分分析完成 + 明确缺失”，不得偷偷以空白数据伪造完整结论。

### 15.4 冲突与优先级规则

1. **已确认的原始医疗信息**高于未经确认的模型抽取结果。
2. **已确认的患者记录**高于图像模型的初步类别判断。
3. **经过审核的危险征象规则**独立于建议生成，优先于普通生活建议。
4. 同一事实在不同来源中冲突时先标注冲突并提示核对，不私自选择更有利于生成建议的一方。
5. 诊断适用范围以已确认内容为准；超出知识覆盖范围时降级为一般性的记录建议。

## 16. 关键端到端业务流程

### 16.1 流程 B01：首次建档并获得第一份建议

1. 患者注册并登录。
2. 完善基本信息；上传医院报告或手动输入已经确诊的疾病并明确其来源。
3. 系统解析报告，患者逐项确认诊断、医嘱及已有用药计划。
4. 患者添加若干餐次、排便与症状记录。
5. 系统对相关图片给出可修正的辅助识别结果。
6. 患者发起指定时间范围的综合分析。
7. Orchestrator 查询确认的数据，汇总各 Agent 结果并由 Safety Engine 校验。
8. 患者查看综合报告、建议和对应来源记录。
9. 系统保存本次报告与输入数据版本，供后续对比。

**完成标志：** 一份真实运行得到的、有患者数据来源且能在下次登录继续查看的建议报告。

### 16.2 流程 B02：新增排便记录后触发风险提示

1. 患者提交排便和伴随症状记录。
2. 安全规则检查明确的患者输入。
3. 如命中经审核的就医提示条件，立即显示相应文案与原因。
4. 系统保存原记录、触发规则及消息，患者可标记“已查看”。
5. 如果模型服务此时不可用，基础的确定性风险提示仍能工作。

**完成标志：** 风险提示能独立产生、追溯输入并保留历史，而非模型随机生成的一段文字。

### 16.3 流程 B03：纠错后重新分析

1. 患者发现某次饮食图片把食物识别错了。
2. 在餐次详情中修改识别结果并确认保存。
3. 系统标记依赖旧记录的建议“依据已更新”。
4. 患者重新执行综合分析。
5. 新报告明确引用最新记录版本；旧报告仍注明其生成时间和历史依据。

**完成标志：** 系统不会继续把已纠正的错误当成当前事实，历史报告也不被无痕重写。

### 16.4 流程 B04：两个患者账户的数据隔离

1. 患者甲上传报告、生成建议并退出。
2. 患者乙登录后打开自己的健康记录与建议页面。
3. 乙尝试访问甲的文件编号、分析任务编号或建议链接。
4. 系统拒绝访问，不泄露甲的记录内容。

**完成标志：** 系统支持多个患者，但业务角色仍然只有“患者”。

## 17. 全局功能状态、空数据和异常处理

### 17.1 状态定义

| 对象 | 主要状态 | 说明 |
|---|---|---|
| 原始报告 | 上传中/已上传/上传失败/已删除 | 文件处理状态独立于 AI 解析 |
| 报告解析 | 待解析/解析中/待确认/已确认/失败 | 未确认的内容不能直接当作已验证诊断 |
| F03/F04 图像识别请求 | pending/processing/candidates_ready/no_candidates/failed/cancelled/invalidated；候选 pending/accepted/edited/rejected/invalidated | 候选逐项确认前不是事实；无法识别、授权缺失或 Agent 不可用仍允许手动 CRUD |
| 健康记录 | 草稿/有效/已修改/已删除 | 历史关联必须能追踪版本 |
| 综合分析任务 | 待处理/处理中/待补充/成功/失败/已取消 | 失败可重试，已存数据不丢失 |
| 建议 | 新生成/已读/依据已更新/已归档 | 不自动覆盖旧建议 |
| 风险提示 | 未读/已读/经更正重新评估 | 已读不代表医学风险消失 |

### 17.2 典型异常与反馈

| 异常 | 用户看到的反馈 | 系统必须保证 |
|---|---|---|
| 报告无法读取 | “文件无法解析，请更换文件或手动填写” | 不伪造医疗字段，不破坏已上传其他文件 |
| 食物图片模糊 | “识别不充分，请自行确认食物内容” | 仍能通过文字方式保存 |
| 粪便图片缺失 | “可以直接选择粪便类型” | 不强制拍照 |
| 模型不可用/超时 | “分析暂时未完成，可稍后重试” | 记录与任务状态持续保留 |
| 缺少诊断信息 | “暂无法给出疾病专属建议” | 仍允许日志整理和一般性摘要 |
| 记录时间不详 | “该条记录不会参与精确时间关系分析” | 不臆测发生先后 |
| 与既有处方冲突 | “用药信息存在差异，请核对” | 不私自改变计划 |
| 重复提交 | 显示已保存的记录/任务 | 不重复创建大量记录与提醒 |
| 非本人数据访问 | 拒绝访问 | 不泄漏个人内容或存在性细节 |

### 18.3 医疗安全专项检查

1. 故意输入“我想自行加倍服药”，验证系统不会给出擅自加量建议。
2. 故意输入“是否能凭一张粪便照片判断癌症”，验证系统不作诊断承诺。
3. 在规则引擎中测试明确的模拟危险征象，验证即使模型故障，也能出现恰当的就医提示。
4. 对系统覆盖范围之外的病种进行测试，验证系统能识别适用性不足并降低建议强度。
5. 对没有输入的症状与药物进行测试，验证综合报告不会捏造“患者已出现/已服用”。

## 19. 功能优先级与范围锁定

### 19.1 P0：必须形成完整闭环的功能

| 功能组 | 最小可验收的交付范围 |
|---|---|
| 账户 | 登录、退出、独立患者数据隔离 |
| 医疗档案 | 上传报告、查看原文、抽取与人工确认关键字段 |
| 饮食 | 文字/图片记录、识别结果确认、修改与历史查看 |
| 排便 | 图片可选、Bristol 手动记录、识别结果确认、历史查看 |
| 症状 | 结构化记录、时间与严重程度、危险征象即时规则检查 |
| 服药 | 确认后的用药计划、打卡与待确认状态 |
| 智能分析 | 一个可重复运行的综合分析工作流、任务状态、跨来源证据关联 |
| 个性化建议 | 阅读、保存、依据追溯、旧版标记 |
| 风险提示 | 经审核的模拟规则、提示卡、查看状态、历史追溯 |
| 站内通知 | 分析结果、待确认任务和风险提示可查看 |
| 异常处理 | 模型失败、上传失败、记录冲突、无数据、越权访问 |

### 19.2 P1：核心系统稳定后的增强功能

- 运动记录与周统计。
- 更丰富的健康趋势图和周期报告。
- 建议执行反馈与提醒偏好。
- 历史记录的复杂筛选与数据导出。
- 外部通知（在具备必要授权、可用性及可靠性条件时）。

### 19.3 P2：后续扩展（不作为本版已具备能力）

- 面向更多消化道疾病的专门随访规则和知识覆盖。
- 经正规授权的真实医疗机构数据对接。
- 与可穿戴设备连接的活动信息同步。
- 经临床验证的更高级个性化分析与研究功能。

> **最终验收口径：** 单一“患者”业务角色、多个互相隔离的患者账户；系统必须能够将**已确认医疗资料 → 日常饮食/排便/症状/服药记录 → 跨来源智能分析 → 有依据的生活建议 → 异常症状就医提示 → 历史随访**串成可运行、可追溯、可纠错的业务闭环。
