# GutCare Agent 部署与运维手册

> 版本：V1.0 · 2026-10-14

## 1. 环境与服务

环境为 `local/test/staging/production`，数据和密钥完全隔离。目标 Compose 基线规划包含 `gateway`、`api`、`worker`、`beat`、`postgres`、`redis`、`minio`、`mailpit(local/test)`、`agent-mock(local/test)`；当前仓库根 `compose.yaml` 仅落实本地数据/网关依赖，尚未纳入 API、worker、beat 或 agent-mock，不能当作完整启动拓扑。`compose.phone-demo.yaml` 是比赛实体手机联调专用的隔离 test/demo 路径，见 `手机 HTTPS 演示联调指南.md`，不属于本手册的正式部署方案。生产知识库和智能体服务属于独立部署单元。

公网只开放 Caddy gateway 443。`/api` 转发业务 API；origin-root `/uploads/{capability}` 的 PUT/GET 请求也转发到业务 API，由 API 校验短期 capability 后访问私有 MinIO。该路由不是到 MinIO 的直连或流式数据面路由。MinIO 管理、数据库、Redis、API 进程端口均不公网开放。MinIO Community 从锁定的官方源码 commit 构建，管理使用内网 `mc` CLI，不依赖 Web 管理控制台。

## 2. 配置与密钥

配置以环境注入并在启动时校验。仓库只提交 `.env.example`，不得提交真实 JWT 私钥、数据库/SMTP/对象存储凭据、加密密钥或盲索引 pepper。密钥轮换需支持双读期并记录运行手册。

注册 privacy/health 两种告知的版本和摘要必须来自同一个已校验制品（ADR-0020）。仓库 `contracts/consent/registration-notices.json` 仅供开发/自动化测试，明确未获法律批准。生产部署须提供经隐私/法律负责人签核的同 schema 制品，重算 UTF-8/LF SHA-256 后，原子注入 `PRIVACY_POLICY_VERSION`、`PRIVACY_POLICY_SUMMARY_HASH`、`HEALTH_DATA_PROCESSING_POLICY_VERSION`、`HEALTH_DATA_PROCESSING_SUMMARY_HASH`，并将同一制品编入对应 APP 构建。production 后端缺任一项、摘要非法或使用 test/dev 版本时启动失败。

### 本地 B01-4 认证联调（仅合成数据）

该脚本从系统临时目录中的唯一空工作目录启动迁移、bridge 和 APP live test，并先断言该目录没有 `.env`。迁移设置 `GUTCARE_AUTH_E2E_NO_DOTENV=1` 后不调用 dotenv 或读取仓库 `backend/.env`；bridge 用 `Settings(_env_file=None)`，且只通过绝对 `PYTHONPATH`/脚本路径加载源码。因此这条路径不读取仓库根或 `backend/.env`，finally 只清理路径校验后的本次临时目录。

Windows PowerShell 从仓库根执行 `scripts\test-auth-e2e.ps1`。脚本通过专用 Compose project/随机 loopback 端口启动临时 PostgreSQL 18（`gutcare_business_test`、tmpfs）、Redis（受随机密码保护、tmpfs）和 Mailpit（无持久卷）；迁移使用仓库 pinned CPython/uv 及 PG18 集成门禁同款 Alembic `skip_file_config=True` 路径。由于本环境 Windows 原生 Uvicorn 启动会触发 access violation，API 由 test-only `backend/tests/auth_e2e_http_bridge.py` 提供真实 loopback HTTP：它用 stdlib `ThreadingHTTPServer` 接收请求、以 `httpx.ASGITransport` 调同一个 FastAPI app，仅接受显式 test opt-in 并只绑定随机 `127.0.0.1` 端口。认证不需要对象存储，因此不启动 MinIO/ClamAV。Compose 配置中的角色密码、应用环境的 DB/Redis/JWT/邮箱加密/查找 pepper、以及患者邮箱/密码均逐次随机生成，不读取生产 `.env` 中凭据。脚本拒绝非 development/test-only 的告知制品。

Mailpit 只接受本任务随机合成邮箱。脚本经本机 Mailpit API 读取对应邮件，在内存提取验证/重置令牌并直接 POST；不会输出或保存邮件正文、密码、token 或请求/响应体。bridge 禁止访问日志/请求日志/正文日志，临时 stdout/stderr 只包含启动标志并在 finally 按验证过的精确文件名清除；Compose 清理前逐容器核验 project label，只移除本次 project 的容器/卷，bridge 只按本次 PID 与启动时间核验后停止。端口占用时停止启动，不结束未知进程。该桥接只提供 loopback TCP/HTTP，不等同于 Uvicorn 生产部署或真机网络证据；本地流程仅用于开发/自动化测试，测试告知未获法律批准，不可面向真实患者/生产。

## 3. 发布顺序

1. 验证镜像摘要、SBOM、测试报告、契约兼容、备份恢复点，以及生产注册告知制品的法律签核、哈希校验和 APP/后端构建对应记录；任何一项缺失均阻断发布。
2. 执行向后兼容 Alembic 迁移；禁止自动建表。
3. 部署兼容新旧 schema 的 API/Worker。
4. 执行健康检查与合成患者冒烟。
5. 分批切流并观察错误率、延迟、队列和数据库锁。
6. 数据回填完成后另一次发布收紧约束/移除旧字段。

应用回滚不得回滚已经被新数据依赖的 schema；优先回滚代码并保持扩展字段。破坏性迁移必须有专用前滚修复方案。

## 4. 健康与监控

- `/health/live`：进程存活，不探测外部依赖。
- `/health/ready`：API 数据库可连接、`alembic_version` 与当前 Alembic head 一致，且 F13 删除操作、步骤和对象 inventory 无 pending/overdue/processing/dead-letter 项；否则返回 503。Redis/智能体按降级策略呈现。
- 指标：API P50/P95/P99、5xx/429、连接池、锁等待、队列深度/年龄、任务终态、回调拒绝、对象删除失败、邮件失败、规则执行失败。
- 日志绑定 `request_id/task_id`，禁止患者正文、Token、验证码、图片 URL 和完整 prompt。

运维指标接口为 `GET /ops/metrics`，不属于 APP OpenAPI。默认关闭；仅在内网抓取确有需要时设置 `OPS_METRICS_ENABLED=true` 并通过秘密管理系统注入至少 32 字符的 `OPS_METRICS_TOKEN`。抓取方必须使用 `X-Ops-Metrics-Token` 请求头；未配置、未授权均返回常量 404。不得把该 token 放入 URL、抓取目标标签或代理访问日志。接口只输出低基数 route template/status family、readiness 布尔状态和数据库聚合队列计数/年龄；PG 聚合函数不返回患者标识、任务 ID、对象 key 或正文，API 角色不获得底表读取权限。

Prometheus 告警规则模板位于 `infra/observability/alerts.yml`，覆盖 API 5xx、readiness、worker dead-letter、隐私删除 SLA、导出清理和聚合快照失败。仓库仅交付规则配置与结构检查，不代表生产 Prometheus、告警接收器或阈值已经部署；生产发布前需在目标 Prometheus 版本执行 `promtool check rules infra/observability/alerts.yml`，再配置接收人并演练告警。HTTP 请求/readiness 指标保存在每个 API 进程内；当前未启用 Prometheus multiprocess collector。多 worker 部署必须逐进程抓取并由 Prometheus 聚合，或先单独完成 multiprocess 设计和验证，不能把单进程值误当全实例值。

告警处置：API 5xx/延迟上升时先按 route template/status family 查部署与依赖变化，不把患者信息加入标签；readiness 告警检查 DB/schema/privacy replay；dead-letter 或积压年龄增长时检查对应独立 worker、数据库连接与对象存储，再依据队列专属重放/补偿手册处理。隐私删除 overdue 是 SLA 事件，应优先恢复 privacy worker 并核对 replay 门禁；export cleanup 延迟时确认清理 worker 与私有桶生命周期。指标无患者级诊断能力，需使用受控审计工具进一步排查。

## 5. 备份与恢复

PostgreSQL 每日全量 + WAL 归档，目标 RPO 15 分钟、RTO 4 小时；对象存储启用版本/生命周期并独立备份。每月至少一次隔离恢复演练，核对约束、行数、对象可读性、患者隔离和删除账本。备份最长 35 天轮转并加密。

## 6. 故障处理

- 智能体不可用：停止新派发或有限重试，业务 CRUD/规则继续服务，任务显示可恢复状态。
- Redis 不可用：关闭缓存优化，拒绝依赖队列的新异步任务但不伪造成功；从 PostgreSQL 恢复最终状态。
- 对象存储不可用：禁止完成上传，已有结构化数据仍可读。
- 数据泄漏疑似事件：立即隔离凭据/入口、保全去标识审计、启动事件响应和法务/合规流程，不在普通工单复制敏感内容。

## 7. 上线检查

F02 文件清理 worker 以独立进程运行 `gutcare-file-worker`，`WORKER_DATABASE_URL` 必须使用非表所有者的 `gutcare_worker`，不得复用 `DATABASE_URL` 或 bootstrap/migrator 凭据。worker 每 15 秒扫描七天到期文件删除任务、过期上传会话和 orphan cleanup；任务使用五分钟 lease，失败退避重试，worker 重启后超时 lease 可重新领取。Uvicorn `uvicorn.access` 默认 URL 日志在应用初始化时被禁用；不要通过启动配置重新启用，以免泄漏上传/下载 capability path。

F06 物化器通过 `gutcare-medication-materializer` 独立 CLI 使用 `MEDICATION_WORKER_DATABASE_URL`。数据库事务级 advisory lock 与实例唯一键保证可恢复并发，不存在需要清理的 F06 lease；worker 仅查询 active/confirmed 且启用日程并插入 pending 打卡。提醒任务载荷不得含药名、剂量或医嘱。

F12 `gutcare-notification-dispatcher` 独立 CLI 使用 `NOTIFICATION_WORKER_DATABASE_URL` 与 `gutcare_notification_worker` 专用角色；只允许读取普通通知偏好、领取/更新 outbox 和插入患者通知。按分钟调度运行，批次 claim 使用 `FOR UPDATE SKIP LOCKED`，两分钟 lease 可恢复；普通事件失败按指数退避、最多八次后 dead-letter。risk 不受普通开关/quiet hours 影响。不得将 API、通用 worker 或 analysis worker 凭证复用于此角色。

F13 `gutcare-privacy-worker` 使用独立 `PRIVACY_WORKER_DATABASE_URL` 和 `EXPORT_KEK`。数据库或对象存储恢复后，API 必须保持停止/未就绪；先对恢复后的业务库和成对恢复的 MinIO 桶运行 `gutcare-privacy-worker --replay`，仅当退出码为 0 且 pending deletion 已排空后才启动 API。失败时不得绕过门禁开放流量。该单次命令重放 pending/overdue/过期 lease 的删除步骤及版本化对象 inventory；定期恢复演练由 `scripts/test-integration.ps1` 调用隔离 PG18 restore DB 与独立版本化 MinIO 桶验证。`/health/ready` 对上述状态执行只读数据库门禁，不会在请求中执行 replay；生产启动编排仍必须先执行 replay 并检查退出码，不得用 readiness 替代恢复顺序。

F06 0010 为 forward-only 数据变更：来源墓碑首次写入时同事务留下无患者信息的固定迁移 marker；已有墓碑在升级回填时也初始化 marker。downgrade 第一个数据库操作只读该 marker，有值就在任何 RLS/DDL 修改前拒绝，不能将已删除医疗文档伪造回来。应用回滚保持数据库在 0010，回退到经发布流水线验证可运行于 0010 schema 的应用制品；不得回退到只认识 0009 的版本。发布前使用加密 `pg_dump -Fc` 备份 `gutcare_business` 并备份 PostgreSQL globals/角色定义；同时为对象存储启用版本化或取得一致性快照。将数据库与对象备份恢复到隔离环境，核对 Alembic revision、文档/文件/墓碑和幂等快照计数，再执行 backend/integration 门禁；验证通过后才允许切流。故障恢复优先部署兼容应用制品；仅经数据负责人批准后才从成对备份恢复，不对在线 0010 数据库做 downgrade。

恢复演练证据：PG18 integration `test_migrations_round_trip_all_revisions` 覆盖无墓碑 0010→0009→0010、填充 0009 schedule 幂等账本后升级并重放，以及既有软删医疗文档升级时marker初始化；F02/F06 integration 覆盖墓碑存在时 downgrade 被拒、revision 仍为 0010、拒绝前后 RLS/FORCE、policy、constraint、column/schema fingerprint 完全一致且兼容服务继续读取计划。`scripts/test-integration.ps1` 每次创建唯一 Compose 项目、随机端口和全新容器（PG/MinIO 数据仅在 tmpfs），结束只清理本次项目；随后实际执行 `scripts/test-pg18-backup-restore.ps1`，`pg_dump -Fc` 恢复到同一 PostgreSQL 18 实例的新隔离库，检查 revision、行数、患者复合约束及关联查询，再删除临时库/dump。2026-10-15复验成功：revision=`0010_f06_source_refs`，4条计划、2个墓碑、6条幂等账本、2项患者归属约束，关联查询成功。生产全量备份恢复仍须在目标环境包含角色globals和对象存储执行并归档证据。

域名/TLS、CORS、签名 URL、SMTP SPF/DKIM/DMARC、时区、限流、备份、告警接收人、经法律签核的注册告知正文/版本/摘要制品及四项配置核对、生产规则审核、App 签名与商店隐私清单均需完成。仓库 test-only 告知不得改名后用于生产；未经检查不得将 staging 配置直接提升为 production。
